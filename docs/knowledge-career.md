# 知识库扩展：演示与面试材料

以下是本轮新增部分，可与原有问答/运行分析经历合并。已有 Python AgenticRAG、多轮会话、SSE 传输、供应商管理和原有工程基础不是本轮从零原创。请按自己实际参与和理解程度表述，不把 AI 辅助实现全部说成独立原创。

## 简历建议

**AgenticRAG 智能问答与知识库工作台**

在已有 AI 问答系统上扩展 Vue 3 中文知识库工作台，实现本地文档上传、后台索引、限定范围问答、来源定位与历史证据回看，重点展示前端业务建模和前后端异步协作。

技术栈：Vue 3、TypeScript、Pinia、Vue Router、Element Plus、SCSS、Fetch/SSE；FastAPI、SQLite、Chroma、FastEmbed/ONNX、BM25/RRF。语义模型采用现有开源 BGE 中文模型，未训练或提出新算法。

- 将知识库操作拆分为 API、业务类型、共享状态、文档轮询组合函数及展示组件，实现文档上传校验、状态筛选、重复文件反馈和失败重试，覆盖桌面与窄屏操作。
- 对后台索引任务建立明确状态模型，使用请求版本与 AbortController 隔离切库请求，并在离页清理轮询；显示真实阶段及片段进度，区分文档已提交索引与当前重建任务状态。
- 实现问答知识库选择和来源证据抽屉，贯通文档/片段/版本/页码标识、正文引用与原文访问；历史回答保留证据快照，原文删除后明确提示不可用，避免失效资料被静默替换。
- 联动 FastAPI、SQLite 和独立 Chroma 建立上传到检索的业务闭环，支持限定知识库的关键词/真实中文语义融合检索；通过核心冒烟验证重复上传、范围隔离、失败恢复与删除一致性，未以测试数量或未经测量的性能百分比包装成果。

## 3～5 分钟演示脚本

准备：在独立展示知识库放入自己编写的通用资料；不要展示 API Key 或私人文件。语义模式事先下载模型；如果没有真实回答模型，明确演示管理/检索预览，并说明完整回答联调在自动化中使用隔离供应商夹具。不要把夹具结果说成真实模型回答。

1. **0:00～0:40：创建资料空间。** 打开知识库，介绍关键词与语义模式区别，创建“项目交付资料”，上传 Markdown 与文本型 PDF。解释后台阶段来自真实任务记录，未知总量时不画虚假百分比。
2. **0:40～1:30：展示管理状态。** 再上传同一文件，看到重复文件提示；搜索文件名、筛选可检索状态，指出重试/取消和重建时保留旧索引的设计。索引很快时无需伪造等待过程。
3. **1:30～2:20：检索与原文。** 展开检索预览，问“交付前要做哪些检查”，打开证据片段。切换到 PDF 命中时展示实际页码；说明这是证据来源，不是逐句事实核验。
4. **2:20～3:20：问答闭环。** 点击“基于资料提问”，确认所选库，真实配置就绪时提交一次问题。打开来源与运行分析，说明 Retriever 范围由服务端限制、SSE/运行分析是沿用的已有能力。
5. **3:20～4:30：删除与历史。** 删除一份演示文件，回看此前回答的证据快照和“原文不可用”。刷新历史会话，说明库选择会恢复，删除的知识库不会偷偷退回项目源码检索。最后缩窄窗口演示表格和抽屉布局。

## 面试追问要点

**为什么 Pinia 不保存整个上传任务轮询？** 库目录与当前会话的库选择要跨页面共享；文档过滤、上传反馈和请求控制器属于页面/组合函数。派生的过滤结果用 computed，不复制维护两份文档列表。控制器、计时器不持久化。

**切库后旧响应为什么不会覆盖新列表？** 每次读取增加版本号并取消旧请求，成功/失败/收尾都确认版本与离页状态；轮询只在活动任务存在时继续。AbortController 只是浏览器取消，服务端上传或索引可能已经开始，重新进入应读取真实状态。

**文档状态和作业状态为什么分开？** 一个文档可以已有可用索引，同时正在重建。直接把文档改成“失败”会错误隐藏有效索引。后端暂存新 generation，提交时原子切换；前端明确区分旧索引可用与本次任务进度。

**删除是一个 SQL 语句吗？** 不是。先持久化删除标记，使检索立即排除，再由同一工作线程清理向量与文件；部分失败保留可重试状态。查询只接受当前库的已提交 generation，索引任务不能在删除后重新发布文档。

**为什么历史证据不直接读取当前文档？** 当前文档可能被删除或重建，不能用新证据篡改过去回答。历史保存快照和稳定标识，打开抽屉才检查原文是否仍可用。

**语义检索与原有哈希向量有什么区别？** 旧哈希向量是词特征投影，新路径用训练好的 BGE 中文嵌入表达语义。关键词检索仍有精确词匹配价值，RRF 融合排名；这里只集成现有模型，没有算法创新。小样本三种模式均命中，不能宣称语义必然更优。

**为什么没加重排、Celery 或工作流编排？** 当前单用户本地规模缺少引入成本的证据。SQLite 队列和单索引线程已经能与聊天并行，重排会增加资源/延迟；后续先测量具体瓶颈。

**哪些限制要主动讲？** 单进程、有限文档规模，PDF 页解析/ONNX 批次只能协作取消，模型固定且需本地下载；未验证大量数据、真实问答供应商的所有组合路径、公网部署或准确率。基础控件来自 Element Plus，本轮重点是业务状态、证据联动与接口集成。
